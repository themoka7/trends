# 정책 동향 피드 (Policy Signal Feed)

> 정책브리핑은 **발표된 것**을 알려준다. 이 프로젝트는 **준비 중인 것**을 알려준다.

정부·공공기관이 매일 공개하는 행정문서 목록을 관측해, **정책이 발표되기 전 단계의 신호**를
찾아 웹과 메일로 전달하는 서비스입니다.

「A부처가 B정책을 발표했다」가 아니라,
「3개 기관에서 같은 주제의 문서가 이번 주에 7건 — 평소의 4배」를 알려주는 것이 목표입니다.

---

## 어떻게 신호를 찾는가

개별 문서 한 건은 의미가 없습니다. 의미는 **분포의 변화**에 있습니다.

```
목록 페이징 (전건)  ──→  카운터 +1  ──→  버림
                    └─→  룰 필터 통과분만  ──→  저장  ──→  클러스터링  ──→  급증 탐지  ──→  AI 해석
```

| 신호 유형 | 판정 근거 |
|---|---|
| 동시다발 | 여러 기관에서 같은 키워드가 동시에 |
| 급증 | 평소 대비 발생 건수 급등 |
| 신규등장 | 12개월간 없던 키워드의 출현 |
| 상급지시 | `[지시]` 계열 문서의 하달 |
| 예산선행 | 예산 요구·편성 문서의 선행 발생 |

전건을 훑되 **저장하지 않습니다.** 카운터만 올리고 버리고, 룰 필터를 통과한 문서만 상세 저장합니다.
「근무명령부」 3만 건은 어떤 클러스터에도 기여하지 않기 때문입니다.

## 구조

```
 [GitHub Actions]  새벽 배치 — 수집 · 필터 · 통계 · AI 해석
        │
        ├──→ [SQLite / Turso]  카운터 · 키워드 집계 · 통과 문서 (히스토리)
        │
        ▼
 [Airtable]  발행 신호 · 구독자          ──→ [웹훅] → [GAS] → 구독자 메일 (07:00)
        ▲
        │
 [Vercel]  화면 + 서버 라우트 (API 키는 여기에만)
```

| 도구 | 맡는 일 |
|---|---|
| GitHub Actions | 새벽 배치 (Vercel 함수 실행시간 제한을 피해 배치만 분리) |
| Turso (SQLite) | 히스토리 — 기준선 산출용 집계와 통과 문서 |
| Airtable | 사람이 검수하는 표 (신호 · 구독자). **DB로 쓰지 않음** |
| Vercel | 화면 렌더 + Airtable 접근 프록시 |
| GAS | 메일 발송 |
| Gemini API | 문서 **묶음** 해석 (건별 호출 금지 — 무료 등급 요청 수 제한) |

전 구성요소 무료 티어. 자세한 근거와 한도 계산은 [기획서](기획서_정책동향피드.md) §Ⅷ.

## 현재 상태

**Phase 0 — 착수 전 검증 단계.** 수집기 프로토타입(`collector/`)이 동작하며, 나머지는 미착수입니다.

| | 상태 |
|---|---|
| 수집기 (목록 페이징 · 룰 필터 · SQLite 저장) | ✅ 동작 |
| 필터 튜닝 도구 (`analyze.py`) | ✅ 동작 |
| 클러스터링 · 급증 탐지 | ⬜ 미착수 |
| AI 해석 · Airtable 기록 | ⬜ 미착수 |
| 웹 화면 (Vercel) | ⬜ 미착수 |
| 메일 발송 (GAS) | ⬜ 미착수 |

Phase 0 검증 항목(S1~S8)은 [기획서](기획서_정책동향피드.md) §Ⅸ 참조.
그중 **S6(1주치 데이터로 신호를 뽑아 육안 평가)** 가 프로젝트의 성패를 결정합니다.

## 수집기 사용법

```bash
pip install -r requirements.txt
playwright install chromium
```

```bash
python -m collector.run --count-only --days 7        # 일일 유입 건수 측정 (S2)
python -m collector.run --date 20260806 --max-pages 5 # 맛보기 수집
python -m collector.run --date 20260806               # 하루치 수집
python -m collector.analyze --date 20260806 --pages 12 # 필터 튜닝용 분포 분석 (S4)
```

| 옵션 | 설명 |
|---|---|
| `--instt` | 기관구분 — 중앙행정기관(기본) / 광역자치단체 / 기초자치단체 / 교육청 / 공공기관 |
| `--max-pages` | 페이지 수 제한 |
| `--force` | 이미 수집한 날짜 재수집 |
| `--db` | SQLite 경로 (기본 `data/signals.db`) |

### 왜 Playwright인가

목록 AJAX(`infoList.ajax`)를 순수 HTTP로 부르면 HTTP 200에 `code: 491`만 돌아옵니다.
세션 쿠키 · XSRF 헤더 · TLS 핑거프린팅(curl_cffi) · 검색조건 선행 등록을 모두 시도했으나 전부 491.
실제 브라우저 페이지 컨텍스트의 `fetch`만 정상 응답합니다(WAF가 JS 실행 컨텍스트를 요구).
페이지는 1회만 열고 재사용하므로 오버헤드는 최초 1회뿐입니다. — `collector/browser_client.py`

## 파일

```
collector/
  run.py             배치 엔트리포인트 (수집 · 건수 측정)
  browser_client.py  Playwright 기반 목록 수집
  client.py          엔드포인트 정의 · 응답 정규화 (⚠️ 담당자 실명 폐기 지점)
  filters.py         룰 필터 — 보호 규칙 우선, 규칙별 적중 수 집계
  db.py              SQLite 저장 계층 (L0 카운터 / L0b 집계 / L1 문서)
  analyze.py         페이지 균등 표집 후 기관·단위업무·부서 분포 분석
data/
  signals.db         로컬 수집 DB
기획서_정책동향피드.md      설계 문서 (v3, 최종)
기획서_정부정책_AI피드.md   설계 문서 (v1, 소스 검토 — 참고용)
```

## 지키는 규칙

1. **담당자 실명은 저장하지 않는다.** open.go.kr 상세 페이지에는 담당자 실명이 노출됩니다.
   `client.normalize()` 에서 파싱 즉시 폐기하며, 이 경계 밖으로 실명이 나가지 않습니다.
   — 이 프로젝트의 가장 실질적인 법적 위험 지점입니다.
2. **사람이 검수한 것만 나간다.** 배치가 만든 신호는 `published` 체크 전까지 화면에도 메일에도
   나가지 않습니다. 통계 기반 `strength` 와 사람 검수 `published` 를 분리한 이유입니다.
3. **AI 분석 초안임을 항상 고지한다.** 모든 신호 카드에 근거 문서 원문 링크, 강도 수치
   (문서 수 · 기관 수 · 급증률), "AI 분석 초안" 고지 — 이 셋은 타협하지 않습니다.
4. **수집은 예의 있게.** 요청 간격 1~2초 · 동시 요청 1 · 새벽 시간대 · User-Agent에 연락처 명시 ·
   상세 조회는 필터 통과분만. 차단 시 즉시 중단하고 기관에 정식 문의합니다.
5. **API 키는 서버에만.** 읽기 경로도 포함 — 화면에서 Airtable을 직접 호출하지 않습니다.
